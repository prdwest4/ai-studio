## AUTONOMOUS CODING AGENT OPERATING RULES — MANDATORY

این بخش جزء سند و الزام اجرایی پروژه است.

1. این ۷ سند در مجموع یک Source of Truth واحد هستند. Agent باید قبل از هر Phase هر ۷ سند را کامل بخواند و آن‌ها را با وضعیت واقعی Repository تطبیق دهد.

2. Agent نباید برای تصمیم‌های اجرایی معمول، جزئیات پیاده‌سازی، ترتیب کار، تست، Build، Runtime، رفع خطا یا عبور از Phaseها از کاربر سؤال کند.

3. Agent نباید Requirement، قابلیت محصول، Contract، Schema، API، Architecture یا Acceptance Criterion جدیدی از خودش اختراع کند.

4. اگر مسئولیت یک Phase در یک سند به‌تنهایی کامل توضیح داده نشده باشد، Agent باید اطلاعات صریح همان Phase را از مجموع هر ۷ سند و ترتیب رسمی Phaseها استخراج کند. این کار تفسیر اسناد موجود است، نه افزودن Requirement جدید.

5. اگر برای یک تصمیم صرفاً فنی و داخلی چند روش ممکن وجود داشته باشد، Agent باید کم‌خطرترین و کم‌پیچیدگی‌ترین روش سازگار با اسناد را خودش انتخاب کند و از کاربر سؤال نکند؛ مشروط بر اینکه قرارداد محصول یا Scope اسناد تغییر نکند.

6. Agent فقط در این موارد مجاز به توقف و اعلام BLOCKED است:
   - قابلیت اصلی به Integration واقعی نیاز دارد ولی Integration واقعی در محیط موجود نیست.
   - یک Requirement صریح و متناقض در اسناد وجود دارد که بدون تصمیم انسانی قابل رفع نیست.
   - Human Approval طبق اسناد الزام شده است.
   - محدودیت امنیتی یا قانونی مانع اجرای مجاز کار است.
   - خطا پس از Diagnose → Fix → Retest همچنان حل نشده است.

7. در موارد بالا Agent نباید حدس بزند، Requirement جدید بسازد یا از کاربر بخواهد چیزی را طراحی کند؛ فقط BLOCKED و علت دقیق را گزارش کند.

8. پس از PASS شدن یک Phase، Agent باید بلافاصله Phase بعدی را طبق ترتیب رسمی شروع کند. توقف بین Phaseها برای گرفتن تأیید کاربر ممنوع است.

9. Agent باید چرخه زیر را برای هر Phase به‌صورت خودکار انجام دهد:

BUILD → RUN → TEST → VERIFY → FIX → PASS → NEXT PHASE

10. اگر Phase شکست خورد:

STOP → DIAGNOSE → FIX → RETEST

و فقط در صورت حل‌نشدن، BLOCKED شود.

11. Agent نباید به دلیل تمام‌شدن یک پاسخ، Session، پیام یا مرحله، اجرای پروژه را عمداً متوقف کند. معیار توقف فقط قواعد همین سند است.

12. قبل از شروع هر Phase، Agent باید وضعیت Phase قبلی، Commit فعلی، Working Tree و Acceptance Criteria مربوط به Phase را بررسی کند.

13. هیچ Phase بعدی نباید زودتر اجرا شود و هیچ Phase قبلی نباید دوباره‌کاری شود، مگر اینکه برای رفع Failure یا تکمیل Acceptance همان Phase لازم باشد.

14. پس از PASS هر Phase، Commit ایجاد و به branch اصلی Repository push شود؛ سپس Phase بعدی از همان وضعیت واقعی Repository ادامه پیدا کند.

15. گزارش هر Phase باید پس از PASS یا BLOCKED شدن همان Phase ثبت شود و شامل وضعیت واقعی Build، Test، Runtime، Integration و Acceptance باشد.

16. این قواعد برای جلوگیری از پرسش‌های غیرضروری، Scope Drift، اختراع Requirement و توقف دستی Agent ایجاد شده‌اند و در تمام Phaseها لازم‌الاجرا هستند.
